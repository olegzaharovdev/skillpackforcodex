# skillpackforcodex

Набор переиспользуемых skills для Codex.

Этот репозиторий задуман как личная и командная библиотека рабочих навыков: каждый skill оформляет повторяемый процесс в виде короткой инструкции, которую Codex может подхватывать в разных проектах.

## Зачем Нужен Skillpack

В длинных проектах много процессов повторяется:

- закрыть боковой чат протоколом;
- сделать handoff для другой ветки;
- оформить архитектурное решение;
- подготовить ревью;
- создать continuation prompt;
- собрать материалы для статьи или кейса;
- зафиксировать задачи, решения и риски.

Если каждый раз держать такие правила только в переписке, они теряются, устаревают и по-разному исполняются разными AI-сессиями. Skillpack переносит эти правила в файлы, которые можно версионировать, улучшать и устанавливать на другой компьютер.

## Структура Репозитория

```text
skillpackforcodex/
  skills/
    <skill-name>/
      SKILL.md
      agents/
        openai.yaml
      references/
      scripts/
      assets/
```

Обязателен только `SKILL.md`. Остальные папки добавляются, когда skill реально нуждается в метаданных, справочниках, скриптах или шаблонах.

Один Git-репозиторий хранит всю коллекцию. Отдельный `.git` внутри каждой папки skill не нужен.

## Установка

Склонируйте репозиторий:

```powershell
git clone https://github.com/olegzaharovdev/skillpackforcodex.git
```

Скопируйте нужный skill в локальную папку Codex skills:

```powershell
Copy-Item -Recurse -Force `
  ".\skillpackforcodex\skills\<skill-name>" `
  "$env:USERPROFILE\.agents\skills\<skill-name>"
```

Пример:

```powershell
Copy-Item -Recurse -Force `
  ".\skillpackforcodex\skills\sidechat-protocol-pack" `
  "$env:USERPROFILE\.agents\skills\sidechat-protocol-pack"
```

После установки откройте новую Codex-сессию или перезапустите Codex, чтобы skill попал в список доступных.

## Доступные Skills

### sidechat-protocol-pack

`sidechat-protocol-pack` сохраняет боковые чаты Codex в устойчивый файловый пакет. Он нужен для ситуаций, когда в параллельной ветке обсуждается отдельный вопрос, принимаются решения, появляются задачи, формируется промт для основной ветки или рождаются материалы для статьи, курса, Wiki или Project OS.

Skill не обещает восстановить боковой чат как официальный Codex thread. Его задача другая: сохранить смысл, решения, ход мысли и машинно-читаемый снимок так, чтобы результат можно было передать основной ветке, другому ИИ, человеку или будущей системе учета событий.

Примеры вызова:

```text
/protocol
```

```text
Сделай протокол
```

```text
запротоколлируй
```

```text
протокол
```

```text
протокол D:\Путь\К\Папке
```

Первый вызов создает полный protocol pack. Повторный вызов в той же беседе должен создавать addendum/delta и decision diff, не перезаписывая историю молча.

## Слои Sidechat Protocol Pack

### 1. Markdown: слой для человека и основной ветки

Markdown-файлы нужны для чтения, передачи контекста и продолжения работы без полного перечитывания бокового чата.

Обычно создаются:

- `00_INDEX.md` - карта пакета и быстрый вход в материалы;
- `01_PROTOCOL.md` - основной протокол беседы;
- `02_HANDOFF_TO_MAIN_THREAD.md` - короткая передача результата в основную ветку;
- `03_RAW_TRANSCRIPT_NOTES.md` - аккуратные заметки по исходной переписке;
- `04_QUESTION_MAP.md` - вопросы, развилки и открытые темы;
- `05_DECISIONS_AND_TASKS.md` - решения, задачи, статусы и ответственные зоны;
- `06_ARTICLE_MATERIALS.md` - материал для статьи, обучения, Wiki или кейса;
- `*_ADDENDUM_*.md` - добавления при повторном протоколировании.

Как помогает в работе:

- боковой чат можно закрыть без потери смысла;
- основная ветка получает короткий handoff вместо длинной переписки;
- решения и задачи становятся видимыми;
- можно вернуться к логике обсуждения через неделю или месяц;
- материалы проще использовать в документации, обучении и публикациях.

### 2. JSON: структурный снимок

JSON нужен не для чтения глазами, а для автоматизации. Это нормализованный снимок результата боковой беседы.

В JSON фиксируются:

- тема беседы;
- дата и идентификатор протокола;
- проект и рабочая папка;
- папка с Markdown-протоколом;
- папка с машинным export;
- контекст;
- решения;
- задачи;
- ссылки;
- созданные файлы;
- ограничения;
- пометка, что это не официальный импортируемый Codex thread.

Почему создаем JSON:

- его можно загрузить в Event Ledger, PostgreSQL, RAG, Google Sheets или другую систему учета;
- по нему проще искать решения и задачи без чтения всех Markdown-файлов;
- он дает стабильную структуру для будущих автоматизаций;
- основная ветка или другой ИИ могут быстро понять результат бокового спринта;
- можно строить реестр протоколов, аналитику и карту решений по проектам.

### 3. JSONL: лента событий

JSONL - это формат, где каждая строка является отдельным JSON-событием. Он удобен для журналов, потоковой обработки и будущего Event Ledger.

В JSONL можно сохранять события такого типа:

- сообщение пользователя;
- ответ ИИ;
- принятое решение;
- созданный файл;
- задача;
- ссылка;
- ошибка;
- ограничение;
- обновление протокола.

Почему создаем JSONL:

- события можно добавлять построчно, не переписывая весь файл;
- удобно хранить историю повторных протоколирований;
- проще загружать данные в базы, очереди, пайплайны и аналитические инструменты;
- можно восстановить динамику обсуждения, а не только итог;
- это хорошая основа для будущего Sidechat Session Registry.

### 4. Machine Export Registry: общий учет протоколов

Помимо файлов конкретного протокола, skill может вести машинный реестр в отдельной системной папке, например:

```text
D:\.CodexProtocolsDontMove
```

Идея этой папки: хранить машинные данные отдельно от рабочих документов, чтобы не засорять проектные папки JSON/JSONL-файлами, которые пользователь обычно не читает вручную.

Реестр помогает:

- видеть все созданные протоколы по проектам;
- находить предыдущие обсуждения;
- связывать Markdown-протоколы с JSON/JSONL export;
- в будущем вызывать анализ ранее проведенных протоколов;
- готовить загрузку в Event Ledger, PostgreSQL, RAG или Obsidian-граф.

### 5. Obsidian: навигационный слой знаний

Obsidian - это локальное приложение для ведения базы знаний в Markdown. Его часто используют как личную или командную Wiki: заметки лежат обычными `.md` файлами, могут ссылаться друг на друга через `[[вики-ссылки]]`, иметь теги, YAML-frontmatter и отображаться в графе связей.

В контексте этого skill Obsidian не заменяет Markdown-протокол и не хранит тяжелые JSON/JSONL-архивы. Он нужен как навигационный слой: короткая заметка в vault, которая помогает найти тему, понять смысл обсуждения и перейти к полному protocol pack.

Obsidian-заметка может содержать:

- тему обсуждения;
- дату;
- участников или контур;
- краткое резюме;
- ключевые решения;
- задачи;
- ссылки на Markdown-протокол;
- ссылки на machine export;
- теги проекта, темы и типа разговора.

Как помогает Obsidian-слой:

- боковые чаты становятся частью карты знаний, а не отдельными забытыми папками;
- можно группировать обсуждения по темам;
- можно связывать протоколы с проектами, решениями, статьями и исследованиями;
- пользователь читает чистую заметку, а машинные файлы остаются в системном архиве;
- появляется мост между Codex, Project OS и личной базой знаний.


## Дерево проекта и листочки-спринты

Идеология `sidechat-protocol-pack` строится на простой модели: основной Codex-чат - это ствол дерева проекта, а боковые чаты - короткие ветки и листочки-спринты.

Основная ветка хранит направление проекта, правила, WIP, дорожную карту и принятые интегральные решения. Боковой чат нужен для быстрого отдельного спринта: разобрать вопрос, проверить гипотезу, сформулировать промт, принять локальное решение, собрать материал или подготовить handoff.

Если боковой чат закрыть без протокола, листочек может потеряться: вместе с ним исчезают рассуждения, решения и полезные формулировки. Protocol pack возвращает этот листочек обратно в дерево проекта:

- Markdown сохраняет результат для человека и основной ветки;
- JSON сохраняет структурный снимок для автоматизации;
- JSONL сохраняет ленту событий и изменений;
- Obsidian-заметка помещает тему в карту знаний;
- registry связывает все протоколы и позволяет искать по прошлым боковым спринтам.

Так боковые чаты перестают быть временными черновиками и становятся управляемыми короткими спринтами, которые не засоряют основной чат, но возвращают в проект весь полезный результат.


## Обновление протоколов из главной ветки

JSON и JSONL создаются не только «на будущее». Они нужны для практического сценария: основная ветка Codex может одной командой освежить контекст по результатам разных боковых чатов.

Например, пользователь может вести несколько боковых чатов параллельно:

- один боковой чат исследует архитектуру;
- второй проверяет риск или ошибку;
- третий готовит промт или handoff;
- четвертый собирает материал для статьи или Wiki.

После этого в главной ветке можно использовать команды такого типа:

```text
обнови протоколы
прочитай протоколы
освежи контекст по протоколам
собери решения из протоколов
```

Идея: главная ветка читает registry, Markdown protocol packs и machine exports, затем кратко восстанавливает важные решения, измененные предположения, задачи, риски, ссылки и открытые вопросы. Это помогает не потерять смысл закрытых или удаленных боковых бесед и не заставляет пользователя вручную переносить все handoff-сообщения.

JSON дает структурный снимок: тема, проект, решения, задачи, ссылки, созданные файлы, ограничения. JSONL дает ленту событий и обновлений. Вместе они позволяют основной ветке быстро понять, какие «листочки-спринты» уже были проведены и что из них надо вернуть в ствол проекта.

Технический шум в JSON/JSONL сохранять не нужно. События вида `started`, `accepted`, `sync started` и обычные промежуточные статусы агента не имеют ценности для будущего анализа. В machine export должны попадать только содержательные сообщения, решения, задачи, файлы, ссылки, ошибки, ограничения и факты обновления протокола.

## Рекомендуемая Модель Хранения

Для Markdown-протоколов удобно использовать проектную папку:

```text
.protocols/sidechats/YYYY/YYYY-MM/YYYY-MM-DD_<short_slug>/
```

Или явно указать папку при вызове:

```text
протокол D:\Исследования\20260529 Анализ\Результаты\Kimi
```

Для машинных JSON/JSONL export удобнее использовать отдельный корень вне проектов:

```text
D:\.CodexProtocolsDontMove\exports\YYYY\MM\DD\<protocol_id>\
D:\.CodexProtocolsDontMove\registry\
```

Для Obsidian лучше создавать короткие индекс-заметки внутри выбранного vault, а не складывать туда все машинные данные.

Obsidian vault выбирается отдельно для каждого проекта. Это важно, потому что у одного пользователя может быть несколько хранилищ: большой личный vault, vault конкретного проекта, временный vault исследования или клиентский vault. Поэтому путь к Obsidian-папке хранится в `.codex/sidechat-protocol-pack.json` текущего проекта, а не как одна глобальная настройка на все проекты.

При создании Obsidian index note skill должен показывать в ответе точный путь, куда записана заметка. Так пользователь сразу видит, в какой vault ушло обсуждение, и может заметить ошибку до того, как в базе знаний появится путаница.


## Управление настройками хранения

У `sidechat-protocol-pack` есть отдельный режим для просмотра и редактирования связей хранения. Он нужен, чтобы пользователь мог без ручного редактирования JSON понять и поменять:

- куда сохраняются Markdown-протоколы текущего проекта;
- куда сохраняются JSON/JSONL machine exports;
- включен ли machine export;
- какой Obsidian vault/folder используется для текущего проекта;
- включены ли Obsidian index notes;
- где лежит `.codex/sidechat-protocol-pack.json`.

Команды:

```text
настрой протоколы
настройки протоколов
покажи настройки протоколов
измени папку протоколов
измени папку export
измени vault Obsidian
связи протоколов
```

Этот режим не создает новый протокол сам по себе. Он только показывает или меняет маршрутизацию хранения для текущего проекта.

Пример ответа, который должен давать skill:

```text
Текущие связи протоколов для проекта:

Markdown protocol root:
.protocols/sidechats

Machine export root:
D:\.CodexProtocolsDontMove

Obsidian index root:
D:\Path\To\ProjectVault\Входящее\Диалоги

Config file:
.codex/sidechat-protocol-pack.json
```

Так пользователь видит, куда реально уйдут Markdown, JSON/JSONL и Obsidian-заметки до запуска протоколирования.

## Per-Project Настройки

Некоторые skills могут хранить настройки внутри конкретного проекта, чтобы не смешивать разные рабочие контуры.

Для `sidechat-protocol-pack` используется файл:

```text
.codex/sidechat-protocol-pack.json
```

Пример универсального конфига:

```json
{
  "protocol_root": ".protocols/sidechats",
  "machine_export_enabled": true,
  "machine_export_root": "D:\\.CodexProtocolsDontMove",
  "obsidian_enabled": false,
  "obsidian_dialog_root": ""
}
```

Тогда итоговые Markdown-папки будут создаваться так:

```text
.protocols/sidechats/YYYY/YYYY-MM/YYYY-MM-DD_<short_slug>/
```

Для проекта со своим контуром протоколов можно задать другой путь:

```json
{
  "protocol_root": "AiDrevo_OS/01_Protocols/SideChats",
  "machine_export_enabled": true,
  "machine_export_root": "D:\\.CodexProtocolsDontMove",
  "obsidian_enabled": true,
  "obsidian_dialog_root": "D:\\Path\\To\\ObsidianVault\\Входящее\\Диалоги"
}
```

Если project config отсутствует, skill должен спросить, куда сохранять протоколы для текущего проекта, и предложить сохранить выбор в `.codex/sidechat-protocol-pack.json`.

## Добавление Нового Skill

Рекомендуемый формат:

```text
skills/<skill-name>/
  SKILL.md
  agents/openai.yaml
```

Правила:

- `skill-name` пишется в lowercase kebab-case.
- `SKILL.md` обязателен.
- `agents/openai.yaml` желателен для читаемого отображения в UI.
- Не добавляйте лишние README/CHANGELOG внутрь каждого skill без необходимости.
- Подробные материалы лучше класть в `references/`, если они нужны только иногда.
- Скрипты для повторяемых действий кладите в `scripts/`.
- Шаблоны и ассеты кладите в `assets/`.
